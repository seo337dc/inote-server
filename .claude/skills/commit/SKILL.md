사용자가 커밋을 요청한 상태다. 아래 순서를 그대로 따른다. CLAUDE.md의 규칙이 우선이며 어긋나면 CLAUDE.md가 맞다. (이 레포는 NestJS + Prisma 백엔드다. 프론트 레포 `inote`의 같은 이름 스킬과 체크리스트가 다르다.)

## 1. 브랜치 확인
- `git branch --show-current`, `git status --short`로 현재 상태를 본다.
- `main`이면 커밋하지 않는다. 최신 `origin/main`에서 새 브랜치를 만든다 (`git fetch` → `git checkout -b <브랜치> origin/main`). 만든 뒤 `git branch --unset-upstream`으로 upstream 추적을 끊는다 (안 끊으면 `git push`가 main으로 간다).
- 현재 브랜치가 이번 작업과 무관하거나 이미 main에 병합됐으면(`git branch -r --merged origin/main`으로 확인) 그 위에 커밋하지 않고 같은 방식으로 새 브랜치를 판다.
- 브랜치 이름: `feat/`·`fix/`·`docs/`·`chore/` + 영문 kebab-case 한 줄 요약. 새로 만들 때는 이름을 사용자에게 먼저 보여준다.
- 작업과 무관한 untracked/수정 파일이 있으면 같이 커밋하지 않고 어떻게 할지 묻는다.

## 2. 리팩토링 후보 점검 (코드 변경이 있을 때만)
`refactor-advisor` 서브에이전트를 호출한다. 읽기 전용이고, 체크리스트보다 먼저 돌리는 이유는 여기서 코드를 고치기로 하면 테스트·빌드를 다시 돌려야 하기 때문이다.
- 브리핑에는 목표(이번 커밋 전 구조 점검), 범위(`git diff`·`git diff --staged`로 보이는 이번 작업 파일 — 작업과 무관한 파일은 제외), 하지 말 것(수정·커밋 금지, e2e·migrate·DB에 닿는 명령 실행 금지), 출력 형식(에이전트 정의의 형식)을 쓴다. 에이전트에는 대화 맥락이 전달되지 않는다.
- 보고서의 `파일:줄` 근거는 직접 확인하고 사실로 받아들인다. 확인하지 못한 것은 사용자에게 그렇게 전한다.
- 보고서의 후보 표와 "사용자에게 돌려줄 결정"을 **그대로 보여준다.** 우선순위별 처리:
  - **P0**: 지금 고칠지 사용자에게 묻는다. 모듈 분리·이동, 공개 API·스키마가 바뀌는 제안은 사람이 승인한 뒤에만 고친다. 고치기로 했으면 고친 뒤 3단계 체크리스트를 처음부터 다시 돌린다.
  - **P1**: `docs/todo/`에 기록할지 묻는다 (기능마다 파일 하나, 체크박스).
  - **P2**: 보여주기만 하고 넘어간다.
- 이 점검은 **커밋을 막지 않는다.** 사용자가 "그대로 커밋"이라고 하면 그대로 진행한다. 리팩토링을 임의로 시작하지 않는다.
- 이 결과는 참고용 자체 점검이며 정식 코드 리뷰·QA 판정이 아니다(정식 판정은 Cursor, CLAUDE.md 역할 분담).
- 문서만 바꿨으면 건너뛰고 건너뛴 사실을 PR 초안에 적는다.
- 점검 결과(고친 것, 미룬 것)는 PR 초안의 "알려진 한계·후속"에 반영한다.

## 3. 체크리스트 (이 레포 루트에서, 코드 변경이 있을 때만)
순서대로 실행하고 결과를 그대로 보여준다. 하나라도 실패하면 커밋하지 않고 보고한다.
1. `pnpm test` (단위 테스트 전체)
2. `pnpm run build` (타입 검사)
3. **E2E는 기본으로 돌리지 않는다.** `pnpm test:e2e`는 로컬 기본 `DATABASE_URL`이 **운영 DB(Supabase)**라서 운영 데이터에 닿을 수 있다. 개발 DB(`scripts/dev-db.sh`, `docs/runbooks/local-dev-db.md`)로 띄운 경우에만, 사용자가 요청했을 때 돌린다. 돌리지 않았으면 PR 초안의 테스트 항목에 "안 돌림 + 이유"를 적는다.
- `pnpm lint`는 `--fix`가 붙어 파일을 고친다. 커밋 전 체크리스트에는 없으므로 사용자가 요청할 때만 돌리고, 돌렸다면 `git diff`로 의도치 않은 수정이 없는지 확인한다.
- `prisma migrate`·`db push`는 커밋 단계에서 실행하지 않는다.
- 새 서비스 로직에 `*.service.spec.ts`가 없으면 커밋 전에 사용자에게 알린다. **BE 테스트는 사용자가 직접 작성하는 것이 원칙**이다(Claude는 목록·골격만) — 테스트가 비어 있으면 임의로 채우지 말고 알린다.
- `prisma/schema.prisma`가 바뀌었으면:
  - 모든 `///` 설명이 **한 줄**인지, 마이그레이션 파일(`prisma/migrations/`)이 같이 있는지 확인한다.
  - `pnpm exec prisma generate`로 `prisma/dbml/schema.dbml`을 최신화하고, 그 내용을 사용자에게 보여주며 dbdiagram.io(https://dbdiagram.io/d/inote-6a39fc895c789b8acbdd5d39)에 붙여넣어 달라고 안내한다. **사용자가 반영했다고 확인한 뒤에만 커밋한다.** Claude는 dbdiagram.io에 로그인하지 않는다.
- 이번 작업으로 CLAUDE.md에 적힌 사실(구조·모듈 목록·현재 단계·환경변수)이 바뀌었는지 확인하고, 바뀌었으면 같은 커밋 묶음에서 갱신한다.

## 4. 커밋
- 기능 단위로 쪼갠다. 한 번에 몰아서 커밋하지 않는다. 쪼개는 계획(어떤 파일이 어느 커밋에 들어가는지)을 먼저 보여주고 확인받는다.
- 메시지: `feat:`/`fix:`/`docs:`/`chore:` + 한 줄 요약. 최근 `git log --oneline`의 어투를 따른다.
- 메시지 끝에 시스템이 지정한 attribution 줄을 붙인다.
- `git add`는 파일을 명시해서 한다 (`-A`, `.` 금지). `.env*`(`.env.dev`, `.env.supabase*.local` 포함) 등 시크릿이 들어가지 않았는지 `git diff --cached`로 확인한다. 개인 노트(`backend-interview-notes.*`)는 절대 커밋하지 않는다.
- 커밋 훅이 실패하면 `--no-verify`로 우회하지 않고 원인을 보고한다.

## 5. PR description 초안
커밋 직후 `.github/pull_request_template.md` 형식(개요 / 변경 내용 / 배포 시 주의 / 테스트 / 문서 갱신 / 알려진 한계·후속)으로 채워 **보여주기만 한다.**
- 제목은 커밋 컨벤션과 같게. 커밋을 쪼갰으면 "변경 내용"도 커밋 단위로 묶는다. 본문 끝에 시스템이 지정한 attribution 줄.
- "테스트"는 실제로 실행한 것만 체크하고, 안 한 것(E2E 등)은 이유와 함께 적는다.
- "배포 시 주의"는 마이그레이션(Render는 배포 때 `prisma migrate deploy`가 자동 실행됨), FE 동시 배포 여부(요청·응답 모양이 바뀌면 BE 먼저 / 동시 / FE 먼저 가능), 환경변수, 백필 중 해당하는 것을 반드시 확인한다. 해당 없으면 "없음".
- 이번에 남긴 후속이 있으면 `docs/todo/`에 기록했는지 확인한다.

## 하지 않는 것
- `git push`, PR 생성, 병합은 하지 않는다. 사용자가 따로 요청할 때만 한다. 요청받아도 push는 `git push -u origin <브랜치>`만 하고, `main`으로의 push·force push는 규칙을 상기시키고 확인한다.
- 끝나면 결과(커밋 목록 + PR 초안)만 보고하고 멈춘다.
