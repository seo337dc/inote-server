## 1. 관측 가능성의 세 축

| 축 | 질문 | 형태 | 이 프로젝트 |
|---|---|---|---|
| **로그** | "그 요청에서 무슨 일이 있었나?" | 시간순 이벤트 한 줄씩 | **중심.** 요청/응답·에러를 JSON으로 |
| **메트릭** | "얼마나, 얼마나 자주?" | 숫자 시계열 (요청 수, 지연, 에러율) | 선택(전략 D4) |
| **트레이스** | "시간이 어디서 걸렸나?" | 요청 하나의 호출 경로 | 범위 밖 |

**에러 트래킹(Sentry)**은 로그와 다르다. 로그는 "전부 기록해 두고 검색", Sentry는 "에러를 묶어서(같은 에러는 한 건) 알려 주고 맥락을 붙임". 둘은 경쟁이 아니라 보완 관계다.

**직접 해보기**: 최근 로그인 실패 하나를 떠올리고, 그 원인을 찾으려면 로그·메트릭·트레이스 중 무엇이 필요한지 적어 보라.

## 2. 도구별 역할

```
앱(NestJS) ──JSON 로그──▶ 수집기 ──▶ Loki(저장·검색) ──▶ Grafana(화면)
   │
   └── /metrics ◀── Prometheus가 주기적으로 "긁어감"(pull) ──▶ Grafana
```

| 도구 | 역할 | 방식 |
|---|---|---|
| **Loki** | 로그 저장·검색. 본문 전체가 아니라 **라벨만 색인**해서 가볍다 | 로그를 받아서 저장 (push) |
| **Prometheus** | 메트릭 저장. `/metrics`를 주기적으로 가져감 | **pull** — 앱이 숫자를 노출해야 함 |
| **Grafana** | 위 둘을 읽어 검색·그래프·알림 | 조회 |
| **Promtail** | 서버의 로그 파일을 읽어 Loki로 전송 | **2026-03-02 EOL**(공식). 후속 **Grafana Alloy** |

이 프로젝트의 함정: Promtail/Alloy는 "로그 파일이 있는 서버"에서 돌아야 하는데, **Render 무료 서비스 안에는 설치할 수 없다.** 그래서 선택지는 ① Render 대시보드 로그 사용, ② 앱이 Loki HTTP API로 직접 푸시(`pino-loki` 등).

**직접 해보기**: "Prometheus는 pull, Loki는 push"가 의미하는 바를 이 서버에 적용해, 각각 앱에 무엇이 필요한지 한 줄씩 써 보라. (힌트: `/metrics` 엔드포인트)

## 3. Loki 핵심: 라벨과 본문

- **라벨**은 색인된다. 값의 종류가 적어야 한다(`app`, `env`, `level`).
- **본문(JSON 한 줄)**은 색인되지 않고 필요할 때 훑는다. 값의 종류가 많은 `requestId`, `userId`, `path`는 여기에 둔다.
- 라벨에 `requestId`처럼 값이 무한한 것을 넣으면(**카디널리티 폭발**) 성능·비용이 무너진다.

LogQL 맛보기(Grafana Explore에서 쓰는 쿼리 언어):
```
{app="inote-server"}                                 # 이 앱의 모든 로그
{app="inote-server"} |= "ERROR"                      # 본문에 ERROR 포함
{app="inote-server"} | json | status >= 500          # JSON 파싱 후 상태코드 필터
{app="inote-server"} | json | path="/api/v1/blog/posts"
```
공식 문서: https://grafana.com/docs/loki/latest/query/

**직접 해보기**: 로그 한 줄에 어떤 필드를 넣을지(예: `requestId, method, path, status, durationMs, userId`) 정하고, 각각 "라벨 / 본문" 중 어디에 둘지 분류해 보라.

## 4. NestJS 요청 수명주기와 로깅 위치

```
요청 → 미들웨어 → 가드 → 인터셉터(전) → 파이프 → 컨트롤러 핸들러
     ← 인터셉터(후) ←──────────────────────┘
예외 발생 시: 인터셉터의 catchError → 예외 필터 → 응답
```
공식: https://docs.nestjs.com/interceptors

- **인터셉터**: 핸들러 앞뒤를 감싼다 → 소요 시간, 응답 본문, 에러를 한 곳에서 기록하기 좋다. 단 **컨트롤러를 거치는 요청만** 본다.
- **미들웨어**: 라우팅 전에 모든 Express 요청을 본다. 컨트롤러를 거치지 않는 요청도 포함.
- **이 프로젝트의 예외**: `/api/v1/auth/*`는 [main.ts:24-29](../../src/main.ts)의 미들웨어가 `next()` 없이 직접 응답한다 → **Nest 인터셉터에 도달하지 않는다.** 그래서 인증 요청을 기록하려면 미들웨어가 필요하다.
- **함정(미확인)**: 미들웨어가 요청 본문 스트림을 먼저 읽으면 뒤의 Better Auth가 본문을 못 받을 수 있다. 본문은 읽지 않고 메타만 기록하는 게 안전하다.

**직접 해보기**: `main.ts`를 열어 요청이 지나가는 순서를 그림으로 그리고, `/api/v1/blog/posts`와 `/api/v1/auth/sign-in/email`이 각각 어디까지 가는지 표시해 보라.

## 5. 요청/응답 로그 설계 개념

1. **구조화(JSON 한 줄)**: 문장이 아니라 필드로 → 기계가 검색한다.
2. **요청 ID**: 한 요청의 모든 로그를 묶는 키. 헤더(`x-request-id`)로 받거나 서버가 생성해서 응답 헤더로 돌려주면 FE 에러와 BE 로그를 이을 수 있다.
3. **레벨**: 2xx/3xx → info, 4xx → warn, 5xx·예외 → error(스택 포함).
4. **크기 제한**: 큰 본문은 잘라서 기록. Loki는 한 줄 256KB 제한(공식 한도 문서).
5. **fail-open**: 로그 기록·전송이 실패해도 **요청 처리는 절대 실패하면 안 된다.** 로깅 코드는 try/catch로 감싸고 응답 경로를 막지 않는다.
6. **본문 제외 대상**: 인증 경로, multipart 업로드(`uploads/image`, `uploads/post-image`).

**직접 해보기**: 로그 한 줄 JSON 예시를 직접 써 보고(성공 1건, 500 에러 1건), 에러 쪽에 어떤 필드가 더 필요한지 적어 보라.

## 6. 민감정보 마스킹

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **차단 목록(denylist)** | 알려진 위험 키(`password`, `token`…)만 가림 | 구현 쉬움, 디버깅 정보 많음 | 새 필드가 추가되면 **자동으로 새어 나감** |
| **허용 목록(allowlist)** | 안전하다고 정한 키만 남기고 나머지는 가림 | 새 필드가 기본적으로 안전 | 처음엔 정보가 적음 |

이 프로젝트에서 로그에 남기면 위험한 것(조사 2026-10-23): `password`/`newPassword`, `token`류와 `Cookie`·`Authorization`·`x-internal-secret` 헤더, `phone`/`email`, money 모듈의 금액·자산·종목, 글/독서 `content`(큰 필드).

마스킹은 **순수 함수**로 만들면 테스트하기 쉽다(입력 객체 → 가려진 객체). 점검 항목: 중첩 객체, 배열, 순환 참조, 대소문자(`Password`), 값이 아닌 키 이름 기준인지.

**직접 해보기**: 허용 목록과 차단 목록 중 하나를 골라 이유를 적고, 아래 입력에 적용한 결과를 손으로 써 보라.
```
{ "email": "a@b.c", "newPassword": "x", "profile": { "phone": "010..." }, "items": [{ "token": "t" }] }
```

## 7. Sentry와의 관계 (참고)
- FE는 `inote`·`inote-money` 레포에서 Sentry를 붙인다(이 레포 범위 밖). 무료 플랜 한도: 에러 5k, 사용자 1명, 리플레이 50, 조회 30일(가격 페이지, 월 단위는 추정).
- BE에서 `x-request-id`를 응답 헤더로 내려 주면, FE에서 에러 시 이 값을 Sentry 컨텍스트에 실어 **FE 이벤트 ↔ BE 로그**를 연결할 수 있다.
- `SENTRY_DSN`은 현재 코드에서 쓰이지 않는다(`.env.example`에만 있음).

## 용어
- **카디널리티**: 라벨이 가질 수 있는 서로 다른 값의 개수
- **fail-open**: 보조 기능(로깅)이 실패해도 주 기능(요청 처리)은 계속 동작
- **allowlist/denylist**: 허용 목록 / 차단 목록
- **스크레이프(scrape)**: Prometheus가 `/metrics`를 가져가는 일
